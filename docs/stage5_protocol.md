# Stage 5: failure diagnosis and targeted remedies

**Status:** Completed on 2026-08-28. See
[`stage5_results.md`](stage5_results.md).

Stage 5 was added after Stage 4 exposed a large offline-online disconnect: the
three one-step BC checkpoints had nearly identical held-out accuracy, but one
lost every game while two won every game. It is divided into a diagnostic gate
and a remedies experiment so the project does not treat an unverified
explanation as fact.

## Stage 5A: diagnostics

Stage 5A uses frozen Stage 3 checkpoints and does not train or select models.
Its diagnostic environment seeds are 75000-75009, disjoint from dataset
collection, Stage 4 evaluation, recovery collection, and Stage 5B evaluation.

It performs four analyses:

1. **Action alias audit.** Recompute each BC checkpoint's raw six-action test
   accuracy, four-action canonical accuracy, action confusion matrix, and
   pairwise checkpoint agreement. The canonical mapping is
   `NOOP, FIRE, RIGHT, LEFT, RIGHTFIRE, LEFTFIRE -> 0, 1, 2, 3, 2, 3`.
   `FIRE` remains distinct because it may be needed to start play.
2. **Synchronized divergence traces.** Run all three BC policies from identical
   seeds in separate deterministic environments. Record the first raw-action,
   canonical-action, and observation divergence, along with action
   probabilities and pixel differences around the first divergence.
3. **Environment parity audit.** Evaluate every BC checkpoint both with the
   Stage 4 environment and with the exact Atari preprocessing/no-op wrapper used
   during Stage 2 collection. This tests whether wrapper mismatch contributed to
   the apparent trajectory drift.
4. **D3PM reverse-chain audit.** For all 21 D3PM checkpoints, measure noisy-token
   accuracy, predicted-clean-token accuracy, first-action accuracy, and entropy
   at every reverse step on validation examples. This identifies where sampling
   loses information relative to direct denoising.

Stage 5A writes resumable artifacts under `runs/stage5a/` and records explicit
recommendations in `summary.json`. Canonical-action and DAgger experiments are
enabled only if their corresponding diagnostic gate fires. The architecture
control always runs because it is necessary to distinguish diffusion effects
from chunk-prediction effects.

## Stage 5B: remedies and controls

Stage 5B implements three model families:

- **Canonical BC:** one-step BC trained with four semantic action classes,
  merging `RIGHTFIRE` with `RIGHT` and `LEFTFIRE` with `LEFT`.
- **One-round DAgger BC:** the frozen Stage 3 BC policies execute on new seeds
  76000 onward while the deterministic expert labels every student-visited
  state. These recovery examples are aggregated with the original v3 training
  set. They are used only for `H=1`, because future counterfactual expert labels
  would not align with transitions generated by student actions.
- **Chunk BC control:** a direct non-diffusion transformer chunk predictor with
  the same vision encoder, width, depth, attention heads, positional tokens, and
  training budget as D3PM. It sweeps `H = {1, 2, 4, 8, 16, 32, 64}`.

Each family uses training seeds 0, 1, and 2. Training retains offline validation
checkpoint selection. After all checkpoints are frozen, model-family selection
uses 20 fixed collection-matched online episodes with seeds 80000-80019. The
predeclared ranking is mean return, win rate, lower inference latency, then
lexicographic family name. Only the selected family and the original raw BC
reference are evaluated on the untouched final seeds 90000-90099. A random
policy is evaluated on those same seeds.

For a valid architecture comparison, the frozen Stage 3 D3PM checkpoints are
also reevaluated with the collection-matched wrapper on the 20 selection seeds.
This is a post-selection diagnostic control and cannot retroactively win model
selection. It corrects the environment mismatch discovered by Stage 5A without
touching the final 100-seed test set for an unselected family.

This separation ensures that the final 100 episodes are not reused for choosing
a remedy. Generated recovery data, checkpoints, and rollout results remain
under `runs/stage5b/` and are excluded from Git.
